# Java 工程开发规约学习笔记

> 资料定位：本笔记依据一份国内大厂公开发布的 Java 开发规约手册的章节结构整理而成。该手册以"强制 / 推荐 / 参考"三级条目写成，是工程实践导向的编码铁律集合。正文全部用自己的语言重写，不出现任何机构与版本品牌名，代码示例均为手写标准写法。

---

## 一、编程规约：代码怎么写才算合格

### 命名

命名是代码可读性的第一道门。统一规则：

- 类名用大驼峰（`OrderService`），方法名、变量名用小驼峰（`getOrderById`、`orderCount`），常量全大写下划线分隔（`MAX_RETRY_COUNT`）。
- 包名全小写，`com.company.project.module` 层层递进。
- 抽象类以 `Abstract` 开头，异常类以 `Exception` 结尾，测试类以 `Test` 结尾——名字里带上类型信息，读代码的人一眼定位。
- 布尔变量不要用 `is` 开头做字段名（序列化框架可能解析出错），方法名可以用 `isXxx()`。

### 常量与魔法值

代码里不许出现裸的数字和字符串字面量（"魔法值"）。`if (status == 2)` 这种写法，三个月后没人记得 2 是什么意思。抽成有名字的常量：

```java
private static final int STATUS_PAID = 2;
if (status == STATUS_PAID) { ... }
```

枚举比常量类更好：类型安全、可带行为。表示"一组固定取值"时优先用枚举。

### 代码格式

- 缩进统一（4 空格或 IDE 默认），大括号风格全团队一致。
- 单行不超过 120 字符，超了就换行，操作符放行首还是行尾团队定死。
- 方法别太长：一个方法超过 80 行就该拆，能用卫语句提前返回就别层层嵌套 if。
- 注释写"为什么"，不写"是什么"：`// 订单状态：1待支付 2已支付` 有用，`// 获取订单` 配在 `getOrder()` 上就是废话。

### OOP 规约

- 字段一律 private，对外暴露 getter/setter；不需要 set 的就别提供，immutable 对象天生线程安全。
- 对外暴露的接口（API）参数能用基础类型就别用包装类，避免意外的空指针；返回集合时返回空集合而不是 null，调用方省一次判空。
- 继承层级别超过 3 层，组合优先于继承；工具类构造器私有化，防止被实例化。
- 慎用可变参数和反射，业务代码里能不用就不用。

### 集合与并发处理

- 集合初始化时指定容量，避免反复扩容：`new ArrayList<>(expectedSize)`。
- 遍历删除必须用 `Iterator.remove()`，别在增强 for 里直接 `list.remove()`。
- 高并发场景用 `ConcurrentHashMap`，别用 `Collections.synchronizedMap` 再手动同步——前者分段锁性能好得多。
- 线程池必须手动创建（`ThreadPoolExecutor`），不许用 `Executors` 工厂方法——后者的无界队列和默认线程数是线上事故的常见来源。线程池要有有意义的名字，方便排查问题。

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        4, 8, 60L, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(1000),
        r -> { Thread t = new Thread(r); t.setName("order-pool-" + t.getId()); return t; },
        new ThreadPoolExecutor.CallerRunsPolicy());
```

## 二、异常与日志

### 异常处理

- 只捕获你能处理的异常：`catch (Exception e)` 一把梭是偷懒，真正关心的是具体类型。
- 不要吞异常：catch 块里什么都不写是最坏的做法，至少记一条日志；往上抛时用有业务含义的异常包装，保留原始堆栈。
- 方法签名上的 `throws` 别挂太多受检异常，调用方会被模板代码淹没；业务异常建议用非受检异常。
- finally 块里只做资源释放，别再抛新异常把原来的异常盖掉。

### 日志规约

- 日志分级要准：ERROR 是需要人处理的故障，WARN 是暂时能忍的异常，INFO 是关键业务节点，DEBUG 只在排查时开。别把 ERROR 当 INFO 打，也别拿日志当 `System.out`。
- 日志内容必须可定位：带上业务主键（订单号、用户 ID），`log.error("支付回调失败, orderId={}", orderId, e)` 比 `log.error("失败了")` 有用一百倍。
- 敏感信息脱敏：身份证、手机号、密码不许进日志。
- 用占位符 `{}` 别用字符串拼接，日志级别没开时拼接白白浪费性能。

## 三、单元测试

### 可测性

代码写完能不能测，是在设计阶段就决定的：静态方法太多、new 对象写死在方法里、依赖没有接口——这三样是单元测试的三大杀手。依赖注入（构造器传参）是让代码可测的最简单手段。

### 测试写法

- 测试类和被测类同包不同源码目录，命名 `XxxTest`。
- 一个测试方法只测一个点，方法名说清楚场景和预期：`testPay_withInsufficientBalance_throwsException()`。
- 用断言不用 `System.out` 人眼看结果；边界值（0、null、空集合、最大值）是测试的重点。
- 外部依赖（数据库、HTTP、时间）用 mock 替掉，单元测试必须快、必须稳定，不依赖外部环境。

覆盖率是底线不是目标：核心业务逻辑分支覆盖要全，但为了数字写无意义的断言是自欺欺人。

## 四、安全规约

- 所有外部输入都是不可信的：SQL 参数一律用预编译（`PreparedStatement` / MyBatis 的 `#{}`），禁止字符串拼接 SQL，这是防 SQL 注入的铁律。
- 输出到页面的内容做 XSS 转义；重定向 URL 做白名单校验，防止开放重定向。
- 密码存储用加盐哈希（如 bcrypt），不许明文、不许可逆加密；密钥、token 放配置中心或环境变量，不许硬编码进代码仓库。
- 文件上传校验类型和大小，文件名不许直接用用户传的；敏感接口加权限校验和频率限制。
- 依赖的第三方库定期升级，有高危漏洞的版本必须升，这是供应链安全的基本功。

## 五、MySQL 数据库规约

### 建表

- 表名、字段名全小写下划线分隔，`order_item` 不叫 `OrderItem`。
- 每张表都要有自增主键 `id`（bigint unsigned），建表三件套：`id`、`gmt_create`、`gmt_modified`，后两个记录行级时间。
- 字段必须 `NOT NULL` 并给默认值——NULL 会让查询、索引、聚合处处是坑；用 `DEFAULT` 而不是靠应用层保证。
- 状态、类型字段用 `tinyint` 存数字码，配注释说明含义；金额用 `decimal`，禁用 float/double。
- 单表字段控制在 50 以内，超了就垂直拆分；大字段（text/blob）拆到扩展表。

### 索引

- 索引不是越多越好：每个额外的索引都拖慢写入。按查询来建，先有慢查询再加索引。
- 复合索引遵循最左前缀原则，把选择性高的列放前面；覆盖索引能避免回表，查询只 select 需要的列，别 `select *`。
- 唯一索引替代"先查后插"的判重逻辑，并发下后者根本防不住重复。
- 索引列上别做函数运算，`where date(create_time) = ...` 会让索引失效。

### SQL 编写

- 显式写列名，禁止 `select *`。
- 分页用"上一页最后一条的 id"做游标，别用大 offset——`limit 1000000, 20` 要先扫一百万行。
- 多表 join 不超过 3 张，字段类型必须一致，否则隐式转换导致索引失效。
- 更新删除必须带 where，先 select 确认影响行数，线上执行前 review。

## 六、工程结构

### 应用分层

经典分层：展现层（Controller，只做参数校验和结果封装）→ 服务层（Service，业务逻辑）→ 数据访问层（DAO/Mapper，只做 CRUD）。层与层之间用 DTO/VO 传数据，领域对象不许穿透到 Controller。

依赖方向只能向下：上层调下层，下层不许反向依赖上层。跨层的调用走接口，方便 mock 和替换实现。

### 二方库管理

- 二方库（团队内部发布的 jar）版本号三段式，`1.0.0` 正式版，`1.0.0-SNAPSHOT` 快照版；线上只依赖正式版。
- 二方库只做无状态的工具和常量/枚举/接口定义，不许塞业务逻辑，更不许依赖具体实现。
- 依赖冲突用 `mvn dependency:tree` 排查，`exclusion` 干掉传递进来的冲突版本，版本号统一在父 pom 的 `dependencyManagement` 里管。

## 七、设计规约

- 先想清楚再写：动手前画个简单的流程图或时序图，复杂逻辑不画图直接写，返工概率极高。
- 接口设计稳定优先：参数能少则少，返回结构一次定好；对外 API 必须做版本管理，`v1`/`v2` 共存一段时间再下线老版本。
- 幂等性：支付、下单这类接口必须保证重复调用结果一致，用业务唯一键（订单号）做去重，而不是靠前端防抖。
- 降级和限流是线上系统的标配：依赖的下游挂了要有兜底，流量突增要有上限，保护自己也保护别人。
- 配置与代码分离：环境相关的（地址、开关、阈值）全部走配置中心，改配置不重新打包。

## 常见坑

1. `Executors.newFixedThreadPool` 无界队列吃光内存——线程池永远手动创建。
2. `SimpleDateFormat` 定义成 static 共用，多线程下日期解析错乱。
3. MyBatis 里用 `${}` 拼接参数，SQL 注入敞开大门；一律用 `#{}`。
4. 事务方法里 catch 了异常又不抛，事务 silently 不回滚，数据一半新一半旧。
5. 日志里打了用户手机号，安全审计直接挂。
6. `select *` 加了个 text 大字段，接口 RT 从 50ms 飙到 2s。
7. 大 offset 分页越翻越慢，用户翻到后面直接超时。

## 学习建议

- 这类规约手册不要通读背诵，当字典用：写代码时对照，Code Review 时对照，踩坑后回来对照。
- 团队落地时先抓 10 条最高频的（命名、魔法值、空指针、SQL 注入、线程池、日志），跑顺了再加。
- 把规约配成 IDE 检查规则（SonarLint 之类），机器能拦的别靠人记。
- 每条"强制"背后都至少有一次线上事故，理解事故原因比记住条文重要。
