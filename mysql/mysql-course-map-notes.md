# MySQL 课程学习地图

这一组视频课，一共九讲。看一遍下来，整条线很清楚：先是把数据库这东西讲明白、把最基础的查法练熟，
然后讲两表之间怎么连、面试里最爱考的行列转换怎么写，再往下钻到存储引擎、索引、慢查询，最后收尾
在一条 SQL 到底是怎么被执行的。顺序是从用到底层，再到底层怎么反过来指导你写好 SQL。

## 一、数据库简介与查询入门

这两讲是整套课的入口。先讲数据库是干什么的：存结构化数据的地方，表是核心单位，行是记录，列是字段，
关系型数据库用 SQL 这一门语言跟它打交道。然后从最简单的查询开始练手：SELECT 列名 FROM 表名，
配上 WHERE 做条件过滤，ORDER BY 排序，LIMIT 取前几行。基础是基础，但真正重要的是养成一个习惯——
写查询之前先想清楚你要的是什么结果集，而不是先想语法。

刚上手最容易犯的错是 SELECT * 随手就写。数据量小的时候没感觉，表一变大，网络传输和内存开销马上翻倍。
记住一个原则：只拿你要的列。这个习惯从第一天就要有，后面讲 SQL 优化时你会发现它又回来了。

```sql
-- 自己手写的练习示例：按部门查出工资最高的前 3 人
SELECT name, dept, salary
FROM employee
WHERE dept = '研发部'
ORDER BY salary DESC
LIMIT 3;
```

## 二、关联查询

单表查熟了，下一步就是多表怎么拼在一起。这讲解决的是真实业务里最常见的问题：数据分散在好几张表里，
比如订单表只有用户 ID，用户名在用户表里，想一次查出来就得做关联。核心是 JOIN：内连接取两边都匹配的行，
左连接保留左表全部、右表对不上的填空值，右连接反过来。

为什么这一讲重要？因为关联查询写错了，结果集悄悄翻倍或者悄悄丢数据，而且你不一定马上发现。
比如一对多关系里被关联表有多行匹配，行数会膨胀；想去重又乱用 DISTINCT，会把真正不同的行也压掉。
值得记住的关键点：写 JOIN 之前，先画清楚两张表的关联关系是一对一、一对多还是多对多，然后用行数
去验证结果集对不对——预期几行，实际几行，对不上就别往下走。

```sql
-- 自己手写的示例：查出每个用户及其订单数（左连接保留没有订单的用户）
SELECT u.name, COUNT(o.id) AS order_count
FROM users AS u
LEFT JOIN orders AS o ON o.user_id = u.id
GROUP BY u.id, u.name;
```

## 三、行列转换面试题

这是一讲专门的面试题型：把行转成列、列转成行。题面通常是一张成绩表，行是（学生，科目，分数），
要求输出成（学生，语文，数学，英语）这种宽表，或者反过来。考的不是背语法，而是看你会不会
用聚合函数配合条件表达式做“透视”。

两种手写套路要练熟。一种是 SUM(IF(...)) / SUM(CASE WHEN...) 做列转行后的聚合透视；
另一种是 GROUP_CONCAT 把多行拼成一个字符串。面试官真正想听的是你讲清楚思路：
先 GROUP BY 定好粒度，再用条件聚合把行“掰”成列。

```sql
-- 自己手写的示例：成绩表行转列（每个学生一行，各科分数成列）
SELECT
    student_name,
    SUM(IF(subject = '语文', score, 0)) AS 语文,
    SUM(IF(subject = '数学', score, 0)) AS 数学,
    SUM(IF(subject = '英语', score, 0)) AS 英语
FROM scores
GROUP BY student_name;

-- 自己手写的示例：把一个学生的各科成绩拼成一行字符串
SELECT student_name, GROUP_CONCAT(subject, ':', score SEPARATOR '；')
FROM scores
GROUP BY student_name;
```

一个细节：SUM(IF(...)) 里 ELSE 分支写 0 还是 NULL，结果不一样。写 0 时缺考的科目会被算成 0 分拉低总分；
写 NULL 时 SUM 会跳过它。面试时主动把这个区别说出来，比只写出 SQL 更加分。

## 四、存储引擎

这一讲往下钻了一层：表的数据到底存在哪、怎么存。MySQL 里管这事的是存储引擎，最常见的两个是
InnoDB 和 MyISAM。InnoDB 支持事务、行级锁、外键，是现在默认也是生产环境的主力；
MyISAM 不支持事务、只有表级锁，读多写少的只读场景历史上用得多。

为什么要学这个？因为很多“玄学问题”的根子都在引擎层：为什么这张表并发一高就卡住（表锁），
为什么宕机后数据丢了（事务没提交、没做崩溃恢复），为什么删了数据文件还不小（空间没回收）。
记住一个关键点：建表时想清楚要不要事务——要事务就用 InnoDB，基本不会选错；
选了引擎之后，它的行为边界（锁的粒度、崩溃后能不能恢复）就是你写应用代码时必须遵守的约束。

## 五、索引

索引是这套课里性价比最高的一讲。概念一句话：给经常被查的列建一本“目录”，查询时先查目录再定位数据，
不用全表一行行扫。代价也有：写数据时要维护目录（插入变慢），目录本身占空间。所以索引不是越多越好，
而是建在刀刃上。

几个必须刻进脑子的点。第一，最左前缀：复合索引 (a, b, c) 能服务 WHERE a = ?、WHERE a = ? AND b = ?，
但单独查 b 就用不上——建索引之前先看查询长什么样。第二，索引列上别做函数运算，
WHERE DATE(created_at) = '2024-01-01' 会让索引失效，改写成范围条件。第三，覆盖索引：
查询要的列全在索引里，数据库连表都不用回，直接从索引拿结果，速度最快。

```sql
-- 自己手写的示例：给订单表的常用查询建复合索引
CREATE INDEX idx_orders_user_time ON orders (user_id, created_at);

-- 这个查询能用上上面的索引（最左前缀 user_id 命中，且是覆盖查询的候选）
SELECT id, created_at FROM orders
WHERE user_id = 1001
ORDER BY created_at DESC
LIMIT 20;
```

执行流程小图（自己画的）：一条查询进来之后大概走这几步

```text
客户端
  │ SQL 文本
  ▼
连接器 ──▶ 分析器（词法/语法解析）
  │
  ▼
优化器（选索引、定连接顺序、估算代价）
  │
  ▼
执行器 ──▶ 存储引擎（按索引/全表取数据）
  │
  ▼
返回结果集
```

优化器那一步是重点：它决定用哪个索引、表先连谁后连谁。你用 EXPLAIN 看到的执行计划，
就是优化器当时做的决定。索引建得对不对，最终都要到 EXPLAIN 里验证。

## 六、慢查询与 SQL 优化

这两讲（慢查询、SQL 优化）是前面所有知识的“实战验收”。思路是先定位再动手：
打开慢查询日志，抓出执行时间超标的 SQL，一条一条看执行计划。常见慢查询的病因通常集中在以下几类：
没建索引、全表扫描、索引失效（列上套函数、隐式类型转换、LIKE 前缀 %）、SELECT * 拖回整行、
深分页 LIMIT 100000, 20 把前面十万行全扫一遍。

优化的手感来自一个顺序：先看能不能加索引解决（成本最低），再看 SQL 能不能改写（避免索引失效、
减少回表、深分页改成游标/上一页末尾 ID 定位），最后才考虑动表结构或拆分。
值得记住的关键点：优化前先能量化——这条 SQL 现在跑多久、改完跑多久，拿着数字说话，
别凭感觉“觉得这样更快”。慢查询日志和 EXPLAIN 就是你的尺子。

```sql
-- 自己手写的示例：深分页改写（用上一页最后一条的 id 做游标，避免大 OFFSET）
-- 慢写法：SELECT id, title FROM articles ORDER BY id DESC LIMIT 100000, 20;
-- 改写后：
SELECT id, title FROM articles
WHERE id < 900001
ORDER BY id DESC
LIMIT 20;
```

## 七、MySQL 的执行原理

最后一讲把整条链路串起来：一句 SQL 从发出去到拿到结果，中间经历了什么。前面画的那张小图就是这讲的骨架：
连接、解析、优化、执行、存储引擎取数。理解这条链路的最大好处是，出了问题你知道去哪一层找：
语法报错去解析层想，选错索引去优化器和统计信息里找，取数慢去存储引擎和索引结构里查，
连接数打满去连接层和应用池配置里看。

还有一个容易被忽略的点：查询缓存。老版本 MySQL 有它，但命中率低、失效频繁，新版本已经拿掉。
别再指望数据库替你缓存结果，缓存这件事交给应用层（比如 Redis）去做，职责分清楚，系统才好排查。

## 学完之后建议的练习顺序

笔记是地图，路还得自己走一遍。按这个顺序练，每一步都有验证标准：先建两三张有关联的表，
把增删改查和排序分页写顺，验证标准是闭眼能写出带 WHERE/ORDER BY/LIMIT 的查询；
然后练 JOIN，验证标准是能说出内连接和左连接的结果集差在哪、用行数证明；
再拿一张成绩表把行列转换的两种写法各写三遍；接着给表加复合索引，用 EXPLAIN 看执行计划里
有没有出现你预期的索引；最后开慢查询日志，故意写几条慢 SQL，再一条条优化掉，
优化前后把耗时记下来对比。走完这一圈，这九讲才算真正落进手里。
